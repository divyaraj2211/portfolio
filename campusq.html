The problem

Thousands of students, one gate, and a paper register

University events like convocations and freshers' welcomes bring thousands of students through a handful of entry points in a few hours. Check-in was manual. Staff matched names against printed lists, which was slow, error-prone and gave organisers no idea who had arrived until the event was over.

Convocation adds another requirement. A graduate has to reach the right room and the right seat, not just get through the gate, and the university needs a record of both for its official files.

The university wanted a system that was fast at the gate, impossible to fool with a reused pass, visible live to everyone running the event, and that produced clean records at the end.

How it works

The convocation check-in flow

The convocation used the full dual-checkpoint flow. The freshers' event used steps 1 and 2 only.

  1. Upload & emailAdmin uploads the student list from Excel with room and seat assignments. Campus Q generates a unique QR pass for each student and emails it automatically.
  2. Gate scanSecurity scans the pass with a USB scanner. The student is validated and marked as entered. A second scan of the same pass is rejected.
  3. Seat scanA coordinator in each classroom scans students at their seats. The scan only succeeds in the student's assigned room.
  4. Fully attendedA student is marked fully attended only when both the gate scan and the seat scan are complete.
Architecture

A small, dependable stack

I kept the system simple on purpose. A single well-run server was easier to make reliable for a one-day, high-stakes event than a distributed setup the university would then have to maintain.

Engineering decisions

The parts that had to be right

Duplicate entries blocked atomically

Two scanners could read the same pass at the same moment, or a student could share a screenshot of their QR code with a friend. If the server first checked whether a student had entered and then marked them in a separate step, both scans could pass the check before either one wrote.

Each scan is a single conditional update in MongoDB that marks the student as entered only if they were not already marked. Exactly one scan wins. Every other attempt is rejected with a clear message for the security guard.

09:41:02 · Gate A✓ Entered
09:41:02 · Gate B✕ Already entered
09:52:17 · Gate A✕ Already entered

Result: no duplicate or fraudulent entries got through at either event.

Room lock for seating

At convocation, each classroom scanner is locked to one room. A seat scan only succeeds if the student was assigned to that room, so a graduate who walks into the wrong classroom is caught immediately and redirected.

Result: no cross-room or incorrect seating scans, and coordinators could see each room fill up live.

Role-based access

Four roles use the system: security, coordinator, admin and superadmin. Each gets a JWT that carries its role, and the API checks it on every request. Security staff see only the scan screen. Coordinators see their own rooms. Admins manage students and reports.

Result: staff with no training could use the system safely on the day, because each person saw only what they needed.

Passes delivered by email

Printing thousands of passes was not an option. Campus Q generates each QR code on upload and sends it through the Microsoft Graph API from the university's own Microsoft 365 account, which gave better delivery than a generic mail server. Staff can also register walk-in students on site and issue a pass instantly.

Result: every pass for both events was delivered automatically, and nothing was printed.

Built to stay up

A one-day event gives you no second chance, so I treated uptime as a feature. The API runs as a Windows service that restarts itself if it stops, behind nginx handling HTTPS. Before each event, the student list, rooms and seats were loaded and checked in advance.

Result: zero downtime across both events, with admins, coordinators and security all using the live dashboard at the same time.

What I learned

Lessons from running it live

  • Correctness under concurrency is a design choice. The duplicate-entry rule had to live in the database update itself, not in application code that checks first and writes later.
  • Operations are part of the product. Service restarts, HTTPS and pre-event data checks mattered as much on the day as any feature.
  • Design for the person holding the scanner. Clear accept and reject messages and role-specific screens made the system usable by staff who had never seen it before.
  • Records are the real deliverable. The post-event export, with gate time, room time, seat and program for every student, is what the university keeps.
